# 刑事案件混装文书解析与检索改造方案（贴合当前 RAGFlow 代码）

## 1. 现状与根因（对应代码）

当前项目已具备两个高价值专用解析器：

- `interrogation`（讯问/询问笔录）解析器，支持头部信息与问答对分块。见 `rag/app/interrogation.py`。
- `indictment`（起诉意见书）解析器，支持触发词分段与证据项抽取。见 `rag/app/indictment.py`。

但现有链路仍是“单文件级 parser 选择”，在混装 PDF（一个 PDF 多份文书）场景会被击穿：

1. 分类器只输出“整个文件一个 parser_id”（`rag/app/classifier.py`）。
2. 任务执行器按单 `parser_id` 调度（`rag/svr/task_executor.py` 的 `CHUNKING_FUNC`）。
3. 文档入库默认一份文档对应一套 parser（`api/db/services/document_service.py`）。

因此，一旦 PDF 内文书类型混杂，就会发生：

- 类型识别误路由；
- 专用解析器吃到错误边界文本；
- 本来更优的定制解析价值被输入噪声抵消。

## 2. 改造目标

将链路从“文件级解析”升级为“子文书级解析”：

- 先切分：`pdf -> sub_documents`；
- 再识别：每个 `sub_document` 单独识别类型；
- 再路由：对子文书选择 `interrogation/indictment/naive` 等解析器；
- 最终保证引用可回溯到 `source_pdf + page_range + block`。

这与 PRD 中“答案可溯源、禁止无证据断言”的目标一致。

## 3. 分阶段实施（4 周）

### Phase A（W1-W2）：输入治理优先——混装 PDF 切分

> 核心原则：先解决边界，再扩类型。

#### A1. 新增“页级边界检测”模块

建议新增：`rag/app/subdoc_splitter.py`

输入：PDF 文本块（可复用 `deepdoc` / `naive` 的文本输出）
输出：

```json
[
  {
    "sub_doc_id": "...",
    "start_page": 1,
    "end_page": 5,
    "doc_type_hint": "interrogation",
    "confidence": 0.87
  }
]
```

规则信号先行：

- 标题词（如“讯问笔录”“起诉意见书”）；
- 首部模板（时间/地点/讯问人/记录人）；
- 页面结构突变（页眉、页码重启等）。

#### A2. 子文书结果写入 metadata

给 chunk 增加统一字段（可先写入 `metadata` / `metadata_obj`）：

- `source_pdf_id`
- `sub_doc_id`
- `sub_doc_type`
- `sub_doc_page_range`
- `sub_doc_confidence`

### Phase B（W2-W3）：统一 Block 层（先通用，后插件）

#### B1. 统一 Block 抽取契约

将各 parser 输出先归一化为 block 序列（至少包含文本 + 位置）。

建议字段：

- `block_type`（header/paragraph/qa_pair/table/list/footer）
- `content_with_weight`
- `positions` / `page_num_int`
- `sub_doc_id`

#### B2. 保持 P0 两类插件优先

- 讯问笔录：继续用 `rag/app/interrogation.py` 的 QA 边界保护；
- 起诉意见书：继续用 `rag/app/indictment.py` 的分段触发词。

其余类型先回落 `naive`，避免类型长尾拖慢节奏。

### Phase C（W3-W4）：检索侧适配子文书粒度

#### C1. 两级召回

1. 先按 `sub_doc` 粗召回（找对文书）；
2. 再按 block/chunk 细召回（定位证据）。

#### C2. 混合召回兜底

- P0 定制解析 chunk 提高权重；
- 低置信度类型自动走“定制 + 通用”双路召回。

## 4. 与现有代码的最小对接点

1. 分类侧：扩展 `DocumentClassifier` 支持“页级/子文书级”接口，而非仅文件级。(`rag/app/classifier.py`)
2. 调度侧：`CHUNKING_FUNC` 外层增加 `sub_document` 遍历调度。(`rag/svr/task_executor.py`)
3. 校验与配置：确保 `indictment` 与 `interrogation` 都在 parser 白名单。(`api/utils/validation_utils.py`)
4. 前端配置：在解析器选项中展示 `indictment`，便于人工指定。(`web/src/constants/knowledge.ts` 等)

## 5. 验收指标（建议）

优先级按“系统可用性 > 字段精细度”：

1. **边界召回率**（是否切出所有子文书起点）；
2. **子文书可追溯率**（检索结果是否可回链到页码区间）；
3. **P0 文书命中率**（起诉意见书/讯问笔录命中 Top-K）；
4. **人工校正率**（低置信样本可一键调整边界并回流训练）。

## 6. 风险与兜底

- **边界切少** > 切多：切少会导致跨文书污染，优先提高边界召回。
- 扫描件文本差：先启用 OCR fallback（当前分类器已有 OCR fallback 机制，可复用）。
- 先不追求全自动：必须保留“低置信边界人工校正入口”，形成数据闭环。

---

这份方案的重点不是“再写更多类型解析器”，而是把输入治理（混装切分）做成平台能力，再让专用解析器以插件方式增量扩展。
