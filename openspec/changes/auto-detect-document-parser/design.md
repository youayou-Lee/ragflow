# 设计文档：自动检测文书类型解析方案

## Context

### 背景
RAGFlow 当前在创建知识库时需要用户预先选择解析方法（parser_id），包含 15 种解析器选择。对于法律案件场景，同一案件涉及多种文书类型（讯问笔录、鉴定报告、起诉意见书等），不同类型需要不同的结构化方案。

### 当前状态
- 知识库创建：用户选择 Built-in 或 Pipeline，内置模式下选择具体解析器
- 文件上传：已有基于扩展名的简单检测（图片→picture，音频→audio，PPT→presentation）
- 现有解析器：`interrogation`（讯问笔录）、`indictment`（起诉意见书）等

### 约束
- 需要兼容现有知识库（已有 parser_id 的 KB）
- 分类延迟不能显著影响上传体验
- 分类准确性直接影响检索效果

## Goals / Non-Goals

**Goals:**
1. 简化知识库创建流程，移除解析方法选择
2. 实现基于内容的文书类型自动识别
3. 支持法律场景的特定文书类型（讯问笔录、起诉意见书等）
4. 保持与现有解析器的兼容性

**Non-Goals:**
- 不修改现有解析器的实现逻辑
- 不支持用户自定义文书类型（暂不）
- 不做跨文件的案件关联分析

## Decisions

### D1: 文书分类策略

**决策**: 采用规则优先 + LLM 兜底的混合策略

**理由**:
- 纯规则方案：快速、无成本，但覆盖有限
- 纯 LLM 方案：准确但延迟高、有成本
- 混合方案：先用规则匹配常见格式，规则无法判断时调用 LLM

**实现**:
```
分类流程:
1. 规则匹配（快速）
   - 标题关键词: "讯问笔录"、"询问笔录" → interrogation
   - 标题关键词: "起诉意见书" → indictment
   - 文档格式特征: 法律条文格式 → laws

2. LLM 分类（兜底）
   - 提取前 2000 字符
   - 调用轻量级模型判断文书类型
   - 返回 parser_id 和置信度
```

**备选方案**:
- 纯规则：简单但覆盖不足
- 纯 LLM：成本高，每次上传都消耗 token
- 训练专用分类模型：效果好但维护成本高

### D2: 分类时机

**决策**: 文件上传时立即分类，同步执行

**理由**:
- 上传时已有文档内容，分类成本低
- 同步执行保证分类完成后才创建文档记录
- 避免异步带来的状态不一致

**实现**:
```python
# document_app.py upload 流程
def upload():
    # 1. 保存文件
    # 2. 调用分类器
    parser_id = DocumentClassifier.classify(binary, filename)
    # 3. 创建文档记录
    doc["parser_id"] = parser_id
```

### D3: 前端简化范围

**决策**: 完全移除 parseType 和 parser_id 选择

**理由**:
- 法律场景用户不需要关心解析技术细节
- 简化 UI 提升用户体验
- 自动分类比用户手动选择更准确

**实现**:
- 移除 `ParseTypeItem` 组件
- 移除 `ChunkMethodItem` 组件
- KB 创建表单仅保留：名称、描述、嵌入模型

### D4: 默认解析器

**决策**: 无法识别类型时使用 `naive` 作为默认解析器

**理由**:
- `naive` 是通用解析器，适用于大多数文档
- 已有成熟实现，风险低
- 用户仍可在文档级别手动修改

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 分类准确率不足影响检索效果 | 提供文档级别的手动修正入口；记录分类日志便于优化 |
| LLM 分类延迟影响上传体验 | 规则优先快速返回；LLM 调用设置超时 |
| LLM 分类增加成本 | 规则覆盖 80%+ 场景；使用轻量级模型 |
| 遗留 KB 兼容性 | 已设置 parser_id 的 KB 保持不变；仅新 KB 使用自动分类 |

## Migration Plan

### 阶段 1: 后端分类服务
1. 实现 `DocumentClassifier` 服务
2. 实现规则匹配逻辑
3. 实现 LLM 分类兜底
4. 添加单元测试

### 阶段 2: 后端 API 改造
1. 修改 KB 创建接口（parser_id 变为可选）
2. 修改文档上传接口（调用分类器）
3. 保持向后兼容

### 阶段 3: 前端简化
1. 移除 parseType 选择组件
2. 移除 parser 选择组件
3. 更新表单验证逻辑

### 阶段 4: 验证
1. 使用 Playwright 进行端到端测试
2. 验证分类准确性
3. 验证上传流程正常

### 回滚策略
- 后端：通过 feature flag 控制是否启用自动分类
- 前端：保留旧组件代码，通过配置切换显示
